# Выпуск витрины

Ветка `release/storefront` содержит исходник магазина, а `main` — рабочие процессы выпуска. После слияния в ветку витрины GitHub запускает Quality и готовит кандидат для проверенного SHA. Входные данные backend и маршрутизации подготовка читает отдельным SSH-ключом с принудительной командой. При изменении каталога или маршрутов запустите подготовку из `main` с ID проверенного снимка и SHA256 его индекса.

Чтобы опубликовать проверенный кандидат, запустите `Deploy production` из `main` и укажите `candidate_run_id`. SHA и контрольные суммы извлекаются из успешной подготовки. Для отката запустите `Roll back production` из `main` с SHA действующей витрины.

Один раз включите доступ к Beget API и задайте секреты `BEGET_API_LOGIN` и `BEGET_API_PASSWORD` в окружении GitHub `production`. Проверьте доступ запуском `Verify Beget disk quota` из `main`. Перед каждой передачей `Deploy production` читает свежую дисковую квоту через API, считает записи файлового дерева аккаунта и проверяет место и inode файловых систем. Пароль остаётся на runner.

При недоступности API используйте фактический замер из панели Beget. Атомарно обновите закрытый файл `.o100-deploy/account-capacity.json` рядом с document root с полями `measuredAt` (Unix-время замера), `bytes` и `files` (оставшиеся байты и файлы, целые числа). Замер действителен пять минут. При отсутствии свежих данных или нехватке места переключение останавливается. Текущий и резервный выпуски сохраняются.

После переключения проверьте изменённые сценарии при ширине 375 px и на desktop. Следите за ошибками API, ценами, корзиной, заказами и записью в течение первого часа.

[Полный порядок выпуска и отката](https://github.com/mldev92/frames-front-focus/blob/release/storefront/RELEASE_RUNBOOK_RU.md)

## Архивирование выпусков

Для полного выпуска расчёт включает резерв 1 GiB сверх размеров передачи и распаковки. После успешного переключения удаляется проверенная временная копия полного архива на хостинге.

После успешного `Deploy production` workflow `Retain production releases` оставляет действующую версию и непосредственный откат. На runner он проверяет файлы старых выпусков по серверному манифесту, шифрует архивы для `RETENTION_AGE_RECIPIENT`, загружает их в Actions и скачивает обратно для сверки. Удаление проходит под блокировкой выкладки после повторной проверки сервера. При ошибке откройте журнал отдельного workflow хранения. После устранения причины запустите его из `main` вручную. Повторная выкладка витрины не нужна.

Зашифрованные архивы в Actions хранятся до 90 дней. Для более долгого хранения скачайте артефакт со страницы запуска. Для восстановления выполните `age -d -i ~/.ssh/optika_beget -o release.tgz <SHA>.tgz.age`, затем `python3 scripts/verify-retention-archive.py release.tgz <SHA> <manifestSha256>`. Контрольная сумма манифеста указана в соседнем файле `<SHA>.json`. Распаковывайте в отдельный каталог. При замене ключа сохраните доступ к прежнему для восстановления старых архивов.
