# Выпуск витрины

Запустите `Prepare production candidate` из `main`. По умолчанию workflow берёт исходник из `release/storefront`. В поле `storefront_ref` можно указать ветку исправления или SHA. Передайте проверенный манифест backend, его SHA и контрольную сумму действующего `.htaccess`.

Для исправлений интерфейса и новых самостоятельных страниц оставьте поля снимка пустыми. Workflow сравнит код с опубликованным выпуском, возьмёт данные из его HTML и проверит новый кандидат на Apache. Самостоятельную страницу верхнего уровня без загрузчика добавьте в `src/data/standalone-pages.json`. Новые адреса попадут в sitemap при сборке. Изменения каталога, загрузчиков и правил маршрутизации требуют полного пути с ID снимка API и SHA256 его индекса.

Для публикации запускайте `Deploy production` из `main` с frontend SHA из манифеста кандидата, ID подготовки и SHA256 архива. Для офлайн-выпуска workflow сам находит опубликованный родительский манифест и передаёт проверенный пакет изменений. Для возврата к предыдущей версии используйте `Roll back production` с SHA опубликованной версии.

[Порядок подготовки, проверки и отката](https://github.com/mldev92/frames-front-focus/blob/release/storefront/RELEASE_RUNBOOK_RU.md)

## Свободное место и архивы

Перед **полным** выпуском вычтите занятое место NVMe из лимита аккаунта в панели Beget. Передайте остаток в МБ и время замера в поле `beget_free_mb_at` в виде `8000@1795300000` (время — Unix UTC). Замер действителен 15 минут. До отправки workflow проверяет размер обоих архивов, место для распаковки с округлением до блоков и резерв 1 GiB. После успешного полного выпуска workflow повторно сверяет SHA256 и удаляет временную копию архива кандидата на хостинге. Для выпуска кода с опубликованным родителем и для панели администратора это поле можно оставить пустым.

После успешного `Deploy production` workflow `Retain production releases` оставляет действующую версию и непосредственный откат. На runner он проверяет файлы старых выпусков по серверному манифесту, шифрует архивы для `RETENTION_AGE_RECIPIENT`, загружает их в Actions и скачивает обратно для сверки. Удаление проходит под блокировкой выкладки после повторной проверки сервера. При ошибке откройте журнал отдельного workflow хранения. После устранения причины запустите его из `main` вручную. Повторная выкладка витрины не нужна.

Зашифрованные архивы в Actions хранятся до 90 дней. Для более долгого хранения скачайте артефакт со страницы запуска. Для восстановления выполните `age -d -i ~/.ssh/optika_beget -o release.tgz <SHA>.tgz.age`, затем `python3 scripts/verify-retention-archive.py release.tgz <SHA> <manifestSha256>`. Контрольная сумма манифеста указана в соседнем файле `<SHA>.json`. Распаковывайте в отдельный каталог. При замене ключа сохраните доступ к прежнему для восстановления старых архивов.
