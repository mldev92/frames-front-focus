# Сборка без массового чтения production API

Сборки 17.11.2026 создали 69 612 запросов Node к `product.php`. Теперь `build:production` требует проверенный локальный API-снимок. Manifest, prerender и повторные маршруты используют один gateway на loopback. При отсутствии ключа сборка завершается; перехода на live API нет. Это изменение процесса сборки, не кеш цен между запросами покупателей. Браузер и обычный SSR сохраняют прежнее чтение API.

## Состояние внедрения

Изменение подготовлено от фактически развёрнутого frontend `708c2cedb1bfdf0158900ea048a1fd2506a19d69`. Оно начинает действовать в checkout/workflow с этим исправлением. Старые ветки, скачанные инструменты и прямые привилегированные команды автоматически не меняются. До принятия исправления запрещены старые production-сборки и ручные массовые проверки API; прежний catalog-refresh controller остаётся остановленным. Изменение не развёртывает витрину и не открывает 1С.

Нового полного снимка и production-кандидата пока нет. Во время инцидента pause 1С остаётся установленным и запрещает live capture. Снимать pause ради сборки нельзя. Сначала завершить расследование/репетицию и согласовать дальнейший режим 1С; только затем собирать данные в отдельном спокойном окне, без оператора и диагностического permit.

## Получение снимка

Quality CI для pull request больше не запускает legacy `build:beta`, который читал production при локализации ресурсов и SSR-проверках. Он проверяет локальные ресурсы и компилирует витрину с loopback API и запретом внешнего fetch. Этот шаг проверяет компиляцию, не заменяет полную SSR/SEO-приёмку по проверенному снимку и Apache. Отдельные legacy beta-команды не предназначены для инцидентного окна.

1. Обновить и закоммитить полный `deploy/seo-active-products.json.gz` проверенным `refresh-seo-inventory.mjs`. Экспорт использует общий приватный flock и отказывается работать при pause/permit 1С. Возраст inventory — не более 48 часов. Локальные зеркала ресурсов блога должны быть заранее подготовлены и закоммичены; сборка не скачивает их.
2. Опубликовать проверенный SHA с исправлением. Проверить live backend SHA, все файлы backend-манифеста и SHA256 `.htaccess`. Запустить вручную `Capture production API snapshot` на этом SHA с `backend_sha` и `routing_sha256`. Workflow использует существующее защищённое окружение `production`, прежние SSH secrets и общую с выпуском concurrency group `optika100-production`. Ручной CLI: `node scripts/build-production.mjs --capture --snapshot .o100-api-snapshots/capture --host USER@HOST --identity KEY`; backend/routing передаются переменными `O100_BACKEND_SHA`, `O100_ROUTING_SHA256`. Не вставлять ключи в журнал.
3. Capture держит один серверный flock `.o100-production-read.lock` на весь аккаунт. Heartbeat каждые 5 секунд; потеря SSH/свежести более 12 секунд прекращает чтение и сборку. Проверяются pause/permit; предельная длительность lease 8 часов. Это координация наших инструментов, не блокировка остальных процессов хостинга или 1С. Сам guard 1С остаётся отдельным механизмом.
4. Gateway допускает только анонимный GET публичных catalog endpoints и корневых sitemap XML. Один upstream-запрос одновременно, начало не чаще раза в секунду, до 35 000 запросов за запуск, timeout 15 секунд и до 8 MiB ответа. Первый отказ закрывает очередь; автоматических повторов нет. Одинаковые запросы всех дочерних Node-процессов используют одну сохранённую запись; город, раздел и остальные query-параметры не смешиваются. До и после capture сверяются backend/routing и существующий fingerprint каталога. Это не транзакционный снимок всех маркетинговых полей сайта.
5. При 25 тысячах уникальных ответов сбор займёт минимум около 7 часов. Один CI capture ограничен 300 минутами (job — 330); partial artifact сохраняется для продолжения через `resume_run_id`. Продолжать можно только тот же inventory/backend/routing, не позднее 24 часов от начала. Уже сохранённые ответы не запрашиваются заново. Неполный снимок не пригоден для выпуска. Повтор после ошибки требует разбора причины, а не автоматического цикла.
6. Успешный capture печатает SHA256 `index.json`. Зафиксировать SHA и run ID; скачать `production-api-snapshot`. Завершённый снимок неизменяем; каждая запись проверяется по SHA256. Artifact хранится 2 дня, но допустимый возраст снимка остаётся 24 часа. Output capture не имеет разрешающего receipt и не пакуется в релиз.

## Offline-кандидат и выпуск

`Prepare production candidate` принимает обязательные `api_snapshot_run_id` и `api_snapshot_sha256`, скачивает artifact и запускает обычный `build:production`. Для локального replay задать `O100_API_SNAPSHOT` и `O100_API_SNAPSHOT_SHA256`, а также проверенные backend/routing переменные. Нужен чистый закоммиченный checkout; исключение — генерируемые `public/sitemap.xml` и `public/robots.txt`, которые manifest полностью перезаписывает при каждом запуске.

Сборка проверяет полное соответствие origin, SHA256 inventory, catalog fingerprint, backend и routing; отвергает неполные, изменённые, будущие и устаревшие снимки. Prerender retry отключён. Локальная очередь может рендерить несколько страниц параллельно, но production API в replay не вызывается. Ошибка любого этапа не создаёт разрешающий receipt; старый receipt удаляется перед началом.

Успех записывает `generated/api-snapshot-build.json`: frontend SHA, binding, SHA снимка, время и счётчики. Packaging требует replay текущего frontend/inventory/backend/routing, возраст снимка до 24 часов, ноль upstream-запросов и ошибок. `release-manifest.json` содержит `apiSnapshotSha256`. Дальнейшие Apache-проверки, согласование точного артефакта, deploy и rollback остаются обязательными по runbook.

Предзагрузка ограничивает `fetch` в Node, а общий API-клиент перенаправляет только prerender на gateway. Это не системный firewall: новый код с другим сетевым клиентом требует проверки. Произвольные команды, старые checkout и отдельные live инструменты не защищаются автоматически. Catalog refresh теперь требует явно проверенные run ID/SHA снимка; при изменении inventory старый снимок отвергается, требуется новый capture. Автоматический controller нельзя возобновлять без принятия нового source SHA и настройки снимка.

## Проверка изменения

Тесты используют локальный HTTP fixture и PHP CLI, без production API: несколько Node-процессов делят лимит и кеш; replay выполняет ноль upstream-запросов; ошибки, пропуски, checksum drift, устаревание, pause/permit, конкурирующий flock и потеря lease закрывают путь. Проверяется сохранение live-поведения браузера/обычного SSR и отказ packaging для capture/неверного receipt. Полная сборка на реальном свежем снимке остаётся отдельным обязательным этапом принятия кандидата.
